# Stage 8 Spec 3 — Metrics substrate & learner profile

**Date:** 2026-08-05
**Status:** design, approved in conversation
**Depends on:** Spec 1 (KLPs & question generation), Spec 2a (answer-analysis capture), Spec 2b (display)
**Frozen reference:** `docs/ai/error-taxonomy.md`
**Followed by:** Spec 3B (user-tunable settings), Spec 3C (learner dashboard),
Spec 4 (action plan & AI lessons)

---

## 1. Scope

Spec 2a captures per-answer analysis; Spec 2b displays it. Neither turns the
accumulated corpus into a durable model of the learner. Spec 3 does, delivering:

- Pure metric modules: per-KLP BKT, latency index, forgetting curve, session shape.
- A revised **severity** model that separates *what kind* of error from *how bad*.
- The two significance pieces Spec 2a deliberately deferred: `repeatBonus`, and
  deterministic misconception promotion.
- Two learner-facing metrics: **knowledge** and **short-answer readiness**.
- A restructured profile with a new per-topic grain.
- A materialized cache.

**Out of scope:** the `/profile/learner` dashboard, split into Spec 3C. Spec 3
is pure functions and persistence; the dashboard cannot start until they exist,
and keeping them together would delay a working substrate behind UI work.

Nothing here lets the AI *compute* mastery. The AI supplies categorical
judgments and at most one bounded number per tag; every aggregation is
TypeScript.

## 2. Severity: type bands × instance magnitude

### 2.1 The problem

Severity today has two unrelated sources, and neither expresses magnitude.
`severityFromCorruption` (`src/lib/errors/severity.ts`) maps a corruption's
*name* to a fixed 1-5 for MC/TF. Short answer asks the model for an absolute
1-5 with no anchor and no comparison set (`grade-short-answer.ts:78`).

The consequence: a soft, arguably-not-really-an-inversion scores identically to
a true one, and a phrasing slip ("current assets − liabilities", intending
"current assets − current liabilities") is booked as a full `factual_error`.
The error *type* answers "what kind of mistake", which it does well. It was
being overloaded to also answer "how bad", which it cannot.

### 2.2 The model

Each error type carries a `[floor, ceiling]` band. The AI supplies a
**magnitude 1-10** per tag. TypeScript interpolates:

```
severity = round( floor + (ceiling − floor) × (magnitude − 1) / 9 )
```

Choosing bands *is* the act of declaring which type pairs strictly dominate and
which overlap — a band whose floor exceeds another's ceiling always outranks it.

**Magnitude is short-answer-only.** An MC/TF distractor is generated by
instructing the model to corrupt a named KLP with a named corruption, so the
result is by construction a full, clean instance of that corruption. MC/TF
write magnitude `10` and resolve to their ceiling.

### 2.3 The ceilings of five accuracy types are constrained, not chosen

Because MC/TF resolve to the ceiling, the band model is a **provable no-op for
the existing MC/TF path** only if those ceilings equal today's
`CORRUPTION_SEVERITY`. They are therefore pinned:

`conflation` 5, `inversion` 5, `misapplication` 4, `overgeneralization` 3,
`factual_error` 2.

The floors are the new freedom, and are where the magnitude fix lands. The
existing true/false −1 adjustment is unchanged and applies after band
resolution.

### 2.4 Default bands

Accuracy:

| type | band | note |
| --- | --- | --- |
| `conflation` | [3, 5] | ceiling pinned |
| `inversion` | [2, 5] | ceiling pinned; floor carries the soft-inversion case |
| `misapplication` | [2, 4] | ceiling pinned |
| `overgeneralization` | [1, 3] | ceiling pinned |
| `factual_error` | [1, 2] | ceiling pinned; phrasing slips land at 1 |
| `omission` | [2, 5] | SA-only, unconstrained |
| `incomplete` | [1, 3] | milder than omission by construction |
| `unsupported_leap` | [2, 4] | |
| `fabrication` | [3, 5] | inventing a mechanism is never minor |

Clarity: `incoherent_syntax` [2, 5], `disorganized` [2, 4], and `no_thesis`,
`ambiguous_referent`, `undefined_jargon`, `hedging` each [1, 3].

Conciseness:

| type | band |
| --- | --- |
| `kitchen_sink` | [4, 5] |
| `too_terse` | [1, 5] |
| `rambling` | [2, 3] |
| `over_qualification` | [1, 3] |
| `padding` | [1, 2] |
| `redundancy` | [1, 2] |

`kitchen_sink`'s floor sits above `rambling`'s ceiling, so it always outranks
it. `rambling` overlaps `redundancy`, so a severe ramble beats a mild
redundancy. `too_terse` spans the full range because how bad under-answering is
depends heavily on the learner's command of the subject — see §6.3, which is
where that dependency is resolved rather than being baked into the band.

### 2.5 Bands are configuration, not constants

Every function consuming bands **takes them as a parameter**. Spec 3 supplies
the defaults above; Spec 3B overrides them per user without touching call
sites. Importing the table directly anywhere would make 3B a rewrite.

## 3. Completing significance

### 3.1 `repeatBonus`, applied at read

`significance.ts` deliberately omits `repeatBonus` because it depends on
whether the same `(type, target)` recurs in *later* attempts, which do not
exist at write time. Per the frozen reference §3: **+1 when the same
`(type, target)` fired on this KLP within the last 3 attempts.**

Spec 3 applies it in the read path, alongside the recomputed severity. A pure
function takes a tag plus that KLP's recent tag history and returns the
adjusted significance.

### 3.2 Read-time derivation

Per the recompute decision, `severity` and `significance` are **derived at read
time** from stored `type`, `magnitude`, `relevance`, `starred`, and `dimension`.
The stored `severity`/`significance` columns narrow to a fallback for legacy
rows written before `magnitude` existed.

This is a deliberate extension of the rule `significance.ts:34` already states —
store the inputs, not the derived constants — and it is what makes Spec 3B's
knobs retroactive. A user who decides inversions are overweighted sees their
existing profile re-score, rather than waiting weeks for new answers to
outweigh old ones.

## 4. Misconceptions are derived, never emitted

Per the frozen reference §5, implemented exactly as specified:

> Group error tags where `type = 'conflation'` by `(klpId, secondaryKlpId)`.
> At **≥2 occurrences across ≥2 distinct sessions**, promote the pair to an
> active misconception. Retire after **30 days with no recurrence**, or after
> **3 consecutive clean answers on both KLPs**.

The `@@index([klpId, secondaryKlpId, type])` already on `AnswerErrorTag` exists
for this query. Promotion and retirement are a pure function over tag rows;
only the human-readable label is an AI call, made once per promoted
misconception and stored. The `evidence_snippet` is the verbatim `quote`
captured on the triggering tag — stored, never regenerated.

## 5. The pure metric modules

New directory `src/lib/metrics/`. No Prisma, no I/O — mirroring how
`scoring.ts` and `summarize.ts` already carry the math, and following
`profile.ts`'s split of a thin DB shell over a pure shaper.

**`bkt.ts`** — per-KLP Bayesian Knowledge Tracing, replayed chronologically
over a KLP's `AnswerKlpResult` rows, returning `{ pKnown, observations }`.

- The guess rate is **derived**: `guessRate(mode) = 1 − EVIDENCE_STRENGTH[mode]`,
  yielding MC 0.25 / TF 0.5 / SA 0.05. Re-declaring those three numbers is the
  persisted-value-in-two-places drift class this codebase keeps flagging.
- BKT reads `status` and `mode` **unmultiplied, and never the stored `credit`
  float.** `credit` is `STATUS_CREDIT × EVIDENCE_STRENGTH`, two quantities that
  belong in two different positions of the update: `STATUS_CREDIT` in the
  mixing weight, `EVIDENCE_STRENGTH` in `guess` inside the likelihood. Feeding
  the product as the mixing weight applies the mode discount twice and creates
  a **fixed point** strictly below 1 — iterate a correct MC answer and `pKnown`
  stalls there, so a learner answering correctly a hundred times running could
  never be modelled as knowing it. The exact ceiling depends on `BKT_LEARN`,
  `BKT_SLIP` and the mode's evidence strength: ≈0.82 for MC and ≈0.40 for TF at
  the constants below, with no binding ceiling for SA, whose evidence strength
  is too close to 1 to bind. (An earlier draft of this spec said ≈0.76; that was
  a hand calculation that dropped the learning-rate term — it is exactly 10/13
  only when `BKT_LEARN` is 0. Corrected 2026-08-06 after the implementation
  measured the real value.)
- `partial` is soft evidence, interpolated by `STATUS_CREDIT[status]` — the
  categorical fraction only.
- `observations` ships alongside `pKnown` because a one-observation posterior is
  nearly the prior. Nothing downstream may call a KLP weak below
  `MIN_OBSERVATIONS` (3).

**`pace.ts`** — a card's median response time over the learner's own median *in
that mode*. Short answer and true/false differ by an order of magnitude, so a
cross-mode ratio is meaningless. `> 1` is effortful retrieval, `< 1` fluent.
This separates "correct" from "actually known": a card answered right at 2.4×
baseline is not mastered. `null` below `MIN_TIMED_OBSERVATIONS` (3) per mode,
rather than a ratio built on one sample.

**`forgetting.ts`** — an empirical curve, not a fitted one. Consecutive
same-card event pairs bucketed by elapsed gap (`<1d`, `1-3d`, `3-7d`, `7-30d`,
`>30d`), reporting recall rate per bucket with `halfLifeDays` linearly
interpolated at the 0.5 crossing. Deliberately not a fitted exponential: an
optimizer over a handful of sparse pairs returns a decay constant to three
decimals the data cannot support. `null` below `MIN_GAP_PAIRS` (5) total pairs,
and `halfLifeDays` is `null` rather than a number when recall never crosses 0.5.

**`session-shape.ts`** — velocity as items per minute from
`StudySession.durationMs / itemCount`; fatigue comparing the session's first
third against its last third on both accuracy and latency, returning
`{ accuracyDelta, latencyRatio, fatigued }`. Requires ≥6 items — splitting a
4-question quiz into thirds measures noise.

**`misconceptions.ts`** — §4's promotion and retirement, as a pure function.

Every module returns `null` rather than a low-confidence number: missing data
makes a conclusion weaker, wrong data makes it wrong, and only the first is
recoverable by studying more.

## 6. Two metrics: knowledge and short-answer readiness

### 6.1 They are separate, and the second is conditional

1. **`pKnown`** — mode-agnostic knowledge, from BKT across MC/TF/SA.
2. **SA readiness** — *given they know it, will they say it well?*

Not `knowledge × articulation`. Multiplying yields a slightly worse mastery
estimate that nobody can act on. The actionable question is "should this learner
get a short-answer question here?", and the answer lives in the **residual**
between knowing and articulating. A blended number destroys exactly the
distinction the metric exists to draw — *doesn't know it* and *knows it but
can't say it* have different remedies (a lesson or MC drilling versus
short-answer practice).

### 6.2 The signed verbosity index

`CONCISENESS_TYPES` already fails in both directions. Per topic:

```
verbosityIndex = Σ significance(over-tags) − Σ significance(too_terse tags)
```

where over-tags are `rambling`, `padding`, `redundancy`, `over_qualification`,
`kitchen_sink`. Positive means over-talking, negative under-talking, near zero
calibrated — e.g. rambling on accounting, too terse on EV/Equity Value,
calibrated on DCF. `CLARITY_TYPES` supplies a second axis. **This requires no
new AI output**; it is a re-reading of tags already being written.

### 6.3 `too_terse` is conditioned on knowledge

A terse answer is frequently terse *because the learner does not know the
material*. Counting it as an articulation problem would book a knowledge gap as
an expression gap and route the learner to short-answer drilling when they need
the concept — misdiagnosing precisely the case §6.1 exists to separate.

Therefore a `too_terse` tag counts toward the verbosity index **only when
`pKnown` for the associated KLP is at or above
`ARTICULATION_MIN_PKNOWN` (0.6), with at least `MIN_OBSERVATIONS` behind it**.
Below that threshold the tag is still recorded and still scores significance —
it is real — but it is read as evidence of a knowledge gap rather than an
expression gap, and does not pull the topic's verbosity index negative.

0.6 is a starting value, named rather than inlined precisely because it is the
kind of threshold that wants tuning once real tag volume exists. A tag whose
`klpId` is null (an error about the whole answer, not a specific point) has no
`pKnown` to test and is excluded from the index.

The conditioning lives in **TypeScript, not the prompt**. The grading call
already receives a learner-context block, so the model *could* be asked to
weigh terseness against known ability — but that would make an AI judgment
depend on the profile that the same judgment feeds, a loop that is neither
reproducible nor recomputable when bands change. The AI judges magnitude from
the answer text alone; TypeScript owns the knowledge conditioning.

### 6.4 Targeting is exposed, not decided

The metrics expose orderings; they do not pick one. Aiming short answer at
high-knowledge/low-articulation cards (polish what is nearly ready) and aiming
it at knowledge gaps (shore up weaknesses) are both legitimate strategies, and
which is right depends on how far out the interview is. Spec 3 surfaces both
orderings; **Spec 3B adds the setting that selects between them.**

## 7. Profile restructuring

**`LearnerCardProfile`** — the existing `LearnerProfile` in
`src/lib/memory/profile.ts`, renamed. Card grain, from `CardProgress` +
`StudyEvent`. Unchanged in behaviour.

**`LearnerTopicProfile`** — new. Per topic: knowledge rolled up from per-KLP
BKT, plus articulation (SA readiness and the signed verbosity index).

**`LearnerProfile`** — the composite of both, and what prompts receive.

The composite rather than handing the name to the topic profile: CLAUDE.md's
Stage 6 brief defines `LearnerProfile` as the token-capped block injected into
every judgment prompt, and prompts want both grains. Narrowing the name would
leave every existing reference compiling and still reading plausibly while
silently meaning something smaller.

### 7.1 Topics are derived from category `normalizedName`

A topic **is** a `CardCategory.normalizedName` (`normalizeCategoryName` = trim,
lowercase, spaces to hyphens). Categories are set-scoped, so the same concept
exists as separate rows per set; `groupCategoriesByName`
(`src/lib/memory/scope.ts:75`) already collapses them on that key, which is how
`/profile/memory` spans sets without a migration. The topic profile reuses it
rather than introducing a second grouping — keying on category *id* would make
"valuation" three different topics across three sets.

Resolution walks `normalizedName` → matching `CardCategory` rows → their ids →
`CardCategoryAssignment` → cards → `CardKlp` → `AnswerKlpResult` /
`AnswerErrorTag`. Display names come from `groupCategoriesByName`'s
most-common-name logic.

This uses the concept layer already on the books: user-authored categories are
the concept nodes, and KLPs roll up to them. No AI-extracted concept graph.

**Accepted limitation:** normalization handles case and whitespace only, so "EV"
and "Enterprise Value" remain distinct topics. See §11.

## 8. Persistence and caching

### 8.1 Schema

One new column: **`AnswerErrorTag.magnitude Int?`** (1-10). Written explicitly
on every new row — the AI's number for short answer, a literal `10` for MC/TF.
**Null therefore means "legacy row" and nothing else.** Were MC/TF to write
null, a pre-migration row would be indistinguishable from a full-magnitude one,
and only the former needs the fallback path.

A materialized per-KLP BKT state table (posterior, observation count, last
applied answer) backs §8.2.

### 8.2 The cache is incremental, not invalidated

BKT is an incremental update by construction: the posterior after N
observations is a function of the posterior after N−1 and the new observation.
The stored posterior is therefore **stepped forward** on each answer — one row
update per KLP touched — and never invalidated-and-replayed.

Full replay is needed in exactly two cases, both rare, bounded, and per-KLP:

1. A band change on a Spec 3B settings save, since severity and significance
   are read-time derived.
2. Re-analysis of an already-recorded answer, which exists via Spec 2a's
   resubmit cascade.

Non-incremental aggregates — the forgetting curve, the verbosity index, topic
rollups — are recomputed after session end via `after()`, the pattern KLP
extraction already uses.

### 8.3 Metrics come from a different grain than the card profile

Spec 3's metrics read `AnswerKlpResult` / `AnswerErrorTag` — KLP grain, and
quiz-only. The existing profile reads `CardProgress` / `StudyEvent` — card
grain, all modes. These get a **parallel pure shaper**, not an extension of
`shapeLearnerProfile`; extending it would make a function that needs two
queries need five, and couple card memory to quiz analysis for callers wanting
only the former.

## 9. The prompt block and its token budget

`shapeLearnerProfile`'s buckets are deliberately uncapped — every qualifying
card is surfaced — bounded only by `RECENT_EVENTS_FETCH_CAP`. That is
survivable at card grain. At KLP grain it is not: KLPs run 1-5 per card, so the
same learner yields several times the content, against a requirement for a
*token-capped* profile.

**KLPs therefore stay out of the prompt block.** It carries only derived,
ID-free, hard-capped lines: the top handful of weak KLP *texts* (subject to the
3-observation floor), per-topic verbosity calibration, active misconception
labels, and pace outliers. A specific KLP's posterior is computed on demand at
the call site that needs it.

The existing `learnerContextBlock` / `distractorMemoryHint` phrasings in
`src/lib/ai/prompts/shared.ts` are reused unchanged; only the block's content
grows.

## 10. Read API for the dashboard

Spec 3 ships the read functions Spec 3C renders, so the dashboard is a
presentation layer over an already-tested surface rather than a place where new
aggregation logic accretes: per-topic rollups, weak KLPs with their evidence
quotes, active misconceptions, forgetting/due state, and pace outliers — each
accepting a `HistoryScope` so 3C never filters in the component.

The dashboard itself is Spec 3C.

## 11. Testing

Pure shapers are unit-tested over in-memory fixtures with an injectable clock,
following `tests/memory/profile.test.ts`. Two properties pinned specifically:

- Derived guess rates equal `1 − EVIDENCE_STRENGTH` for all three modes, so a
  change to either side is a build failure rather than silent divergence.
- **Default bands reproduce today's `CORRUPTION_SEVERITY` outputs exactly for
  MC/TF**, making the band model a provable no-op for the existing path until
  someone tunes it.

Plus: BKT's fixed-point regression (a long run of correct MC answers must
converge toward 1, not stall at the constant-dependent ceiling described in §5);
misconception promotion and retirement
boundaries; `too_terse` excluded from the verbosity index below the knowledge
threshold; and legacy rows with null `magnitude` falling back to stored
severity.

## 12. Deviations from the frozen taxonomy reference

`docs/ai/error-taxonomy.md` is frozen, so changes against it are recorded
rather than made silently.

- **§3 states `severity` is "AI, per instance", 1-5.** It becomes
  band × AI-magnitude. The AI still supplies exactly one number per tag; its
  range widens to 1-10 and its meaning narrows to *degree within a named type*.
  Significance's arithmetic is unchanged, because severity remains 1-5.
- **§4 states MC/TF severity is "corruption severity rank, adjusted by the
  mode's guess rate".** The shipped `severityFromCorruption` already deviates:
  it docks true/false one point for a different reason, and explicitly notes
  that a guess-rate adjustment applies to *correct* answers, not wrong ones —
  a wrong answer is a deliberate choice, not luck. Spec 3 keeps the shipped
  behaviour and treats the doc's wording as superseded.

## 13. Deferred

**Spec 3B — user-tunable settings.** The severity bands become adjustable knobs
under AI settings, and the targeting strategy of §6.4 becomes a selectable
option backed by its own ranking formula. Requires a per-user settings model,
which does not exist today (`User` has no settings relation). Needs validation
(floor ≤ ceiling, within 1-5) and reset-to-default; shipped constants remain the
defaults, so a user who never opens the panel is unaffected.

**Grading conviction and follow-up questions.** The grader has no notion of how
*confident* it is that the learner is wrong. A sloppily-phrased but correct
answer ("current assets − liabilities", intending current liabilities) is booked
as a factual error. The intended feature: where conviction is low, ask a
follow-up before recording a tag. This is the same root defect as §2 one level
deeper — magnitude fixes *how bad we claim it is*, conviction fixes *whether we
were right that it is wrong at all*. A false tag is worse than a missing one,
because it propagates into BKT, misconceptions, and the profile, teaching the
system a weakness that does not exist. §2's model should leave room for a
confidence signal to enter without a rewrite.

**First-class `Topic` model.** Explicitly wanted later. Buys cross-set rename
and merge, synonym aliases ("EV" = "Enterprise Value"), and per-topic metadata.
Deferred safely because the topic key is the same string either way, making the
upgrade additive rather than a migration of meaning.
