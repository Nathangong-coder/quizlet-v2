# Teacher / Classroom Insights (Future Stage — Ideas, Not Yet Scheduled)

**Status:** Speculative. Not designed, not scoped, not slotted into the numbered stage sequence
in CLAUDE.md. This is a brainstorm to revisit once teacher accounts are worth building, not an
implementation plan ready to execute.
**Date:** 2026-07-26
**Origin:** Came up while designing `2026-07-26-unified-memory-write-path-extension.md`. Fixing
that plan's "non-owned-set history" gap (a student's `StudyEvent` history for a set they don't
own still exists and is theirs to manage) is a natural stepping stone toward this: if individual
per-student history already survives independent of set ownership, the missing piece for a
teacher feature is just an aggregation view over students who share a set, not a data-model
rework.

## The core idea

Today, every set has exactly one owner and memory is entirely private to whoever studies it —
there's no notion of a class, a roster, or a shared view across students. If many students study
the *same* set (a teacher's shared deck), the teacher currently has zero visibility into how the
class as a whole is doing: which cards are widely missed, who's behind, who hasn't started.

The pitch: a **teacher account** that owns (or is granted visibility into) a set, and a
**classroom dashboard** that aggregates the anonymized-or-attributed `StudyEvent`/`CardProgress`
data already being generated by students studying that set — turning a personal study tool into
something a school can justify paying for.

## Why this is plausible without a data-model rewrite

- `StudyEvent`/`CardProgress` are already per-user, per-card, append-only, and source-tagged
  (review/quiz-mc/.../star/self-rating once the current plan lands). Aggregating "how is card X
  doing across everyone who studies set Y" is a `GROUP BY` over data that already exists — no new
  write path needed, only new *read* paths and a permission model for who can run them.
- The unified write path (Stage 6) means every mode already funnels through one place. A
  classroom view is "read access to other users' rows for a shared set," which is squarely a
  permissions/aggregation problem, not a new instrumentation problem.

## What's actually missing (the real scope, when this gets built)

1. **A notion of a class/roster.** Today there's no relationship between users beyond
   "who owns a set." Need: a `Classroom` (or `Cohort`) model with a teacher owner and a list of
   enrolled student users (or an invite-code/join-link flow, which schools are very used to from
   Google Classroom/Kahoot).
2. **Permissioning.** A teacher should see aggregate/per-student data only for students enrolled in
   *their* classroom studying *their* assigned sets — not arbitrary cross-account access. This is
   the piece that needs real design care (and likely a "teacher" role distinct from "student" on
   the `User` model, or a separate `TeacherProfile`).
3. **Assignment, not just sharing.** A teacher picks a set and assigns it to a classroom (with an
   optional due date) rather than just handing out a link — this is what makes it read as
   "homework" instead of "a public deck."
4. **Aggregation views**, roughly in order of usefulness to build:
   - **Per-card struggle heatmap for the class:** which cards have the lowest average confidence/
     mastery across enrolled students, so a teacher knows what to re-teach without reading every
     transcript.
   - **Per-student progress list:** confidence/mastery trend per student for the assigned set,
     sortable to surface who's falling behind.
   - **Completion/engagement tracking:** who has and hasn't started/finished the assignment, last-
     active timestamp — the thing every LMS gradebook already has, so it needs to feel familiar,
     not novel.
   - **Class-vs-student comparison** shown *to the student* ("you're doing better than 70% of the
     class on this card") — a light gamification hook that also nudges engagement without
     exposing individual peers' data.
5. **Privacy/compliance groundwork.** Once minors' study data crosses from "just for them" to
   "visible to an adult who isn't their parent," FERPA/COPPA-style considerations become real
   (US K-12 context). At minimum: a clear data-retention/deletion story for student data, and a
   teacher should never see raw self-ratings or timing data framed as "grades" — surface aggregate
   struggle signals, not a surveillance feed.

## Ideas specifically aimed at making this appeal to schools (not just teachers)

- **Standards/curriculum alignment tags** on sets (e.g. "AP Macro — Unit 3," "CFA L1 —
  Fixed Income") so a department head can see a set maps to a syllabus, not just "some flashcards."
- **Exportable reports** (CSV/PDF) a teacher can attach to a parent-teacher conference or a
  progress-report cycle — schools run on exportable paperwork, and this is a cheap, high-perceived-
  value feature once the aggregation queries already exist for the dashboard.
- **LMS/roster import** (Google Classroom roster sync, or at minimum a CSV roster upload) so a
  teacher doesn't have to hand-invite 30 students one at a time — onboarding friction is the
  actual reason many classroom EdTech tools die before a school ever evaluates the pedagogy.
- **Auto-flagging for intervention:** if a card's class-wide average confidence/mastery is low
  right before a due date, surface it to the teacher proactively ("12 of 24 students are below
  50% mastery on 'Duration' — consider reviewing before Friday's quiz") rather than requiring the
  teacher to go looking. This is the single highest-leverage "AI-native" hook for this feature,
  and it's a natural extension of the existing `LearnerProfile`/mastery machinery — same
  computation, aggregated across a roster instead of one user.
- **Targeted re-assignment:** let a teacher push a focused re-quiz (built from Stage 7's
  `PlanItem`/focus-quiz machinery once that exists) to just the subset of students who are
  struggling on a specific card/topic, instead of re-assigning the whole set to everyone.
- **District/school-level pricing hook:** a per-classroom or per-seat license is the natural
  monetization unit once a `Classroom` model exists — this is what actually gets budget approval
  at the school level (vs. per-individual-teacher credit-card signup, which rarely survives past a
  pilot).
- **Multi-teacher/co-teacher and TA support** for a single classroom, since many real classrooms
  (especially higher ed) have more than one instructor of record.

## Deliberately not scoped here

- No schema, no migration, no task breakdown — this is upstream of a real design spec. When this
  gets prioritized, it should go through the normal brainstorm → design spec → implementation plan
  process, likely as its own numbered stage (candidate: **Stage 8**, after Personalized Learning
  Plans in CLAUDE.md, since aggregate class dashboards make the most sense once individual
  learning plans already exist per student).
- No decision yet on whether "teacher" is a role on the existing `User` model or a wholly separate
  account type — that's exactly the kind of question the brainstorming skill should walk through
  when this is actually picked up.
